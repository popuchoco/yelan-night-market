# 軟體設計說明（SDD）

**文件狀態：** 現行設計基線，依 2026-10-29 程式碼整理。  
**系統名稱：** 夜嵐夜市  
**執行型態：** 瀏覽器端、單人、持續性經營模擬。

## 1. 目的與範圍

玩家經營港邊夜市主店並逐步發展店面、員工、設備、分店及財務能力。系統讓日常營運、每週策略、職安／食安事件與週期性帳務彼此連動。

遊戲以單一瀏覽器存檔為目前範圍，不提供帳號系統、跨裝置同步、多人共同經營或正式會計／保險用途。

## 2. 使用者與主要操作

- **玩家／店主：** 管理菜單、備料、設備、排班、攤型、安全、保險、店面與每週資本配置；處理客訴、職災、顧客意外及食安重大事件。
- **受管理分店：** 可由玩家自營，或在符合條件後交由店長自動處理例行工作。店長事件和其他重大決策仍須玩家選擇。
- **場景操作：** 透過 Canvas 點選主店或分店進入管理；旋轉、傾斜、縮放及拖曳檢視固定場景。

## 3. 核心使用情境

### 3.1 每夜營運

1. 在準備階段選擇今晚菜色，檢視庫存與設備、人員狀況，完成每日公告卡選擇（僅排程夜晚出現）。
2. 開門時記錄固定營運費用，生成當夜顧客與事件。
3. 逐位服務顧客；依訂單消耗食材，更新營收、成本、小費、口碑與熟客。
4. 若發生客訴、職災或食安事件，依事件流程處理；保險保障只對符合條件的事件提供模擬理賠選項。
5. 打烊結算現金與帳務分錄，產生日記與故事選擇；玩家選擇後推進至下一夜。

### 3.2 每週決策

每經過七夜進入策略節點，可依當前資金與店況選擇擴店、招聘、併購、保留現金等方案。週轉金依週期規則限制借用及還款，未還本金持續產生模擬利息。新投入需同時考慮長期租金、人事、能源與進貨收益。

### 3.3 每 30 夜結帳

每 30 夜形成一期，產生主要損益、權益變動、財務狀況及現金流量報表；折舊與攤銷按日提列。保險費在每期首夜依攤型與人員狀態計入；符合條件的離職保單於期末工作底稿調整可收回金額，次期收款沖銷應收。結帳後世界繼續進入下一期。

### 3.4 從頭開始

玩家在遊戲說明最後的「09｜重啟」按下重新開始後，系統只顯示確認視窗，不立即變更狀態。取消或關閉視窗不影響遊戲。確認後關閉兩個對話框，清除目前存檔、舊版存檔與損壞備份，呼叫引擎重置同一個 state root，清空場景顧客、回到營運面板並保存第 1 夜新進度。

若載入結果為 `unsupported-version`，重啟不得呼叫刪除或寫入存檔操作；只重置本次執行中的記憶體 state，並提示較新版存檔完整保留。此路徑不代表可以遷移或讀取該新版存檔。

## 4. 遊戲狀態設計

### 4.1 狀態根

`state.js` 的 `freshState()` 建立遊戲根物件。核心欄位群組如下：

| 欄位 | 內容 |
| --- | --- |
| 進度 | `schemaVersion`、`day`、`phase`、`endingId`、故事／週決策紀錄 |
| 玩家經營指標 | `coins`、`fame`、`regulars`、`cozy`、收入與營業結果 |
| 主店營運 | `stock`、`stockCost`、`equipment`、`staff`、`upgrades`、`expansions` |
| 店面組合 | `acquisitions`、`acquisitionTypes`、`outlets[]`；主店與分店保有各自商品、人員、設備、保險和營業狀態 |
| 事件與菜色 | 已解鎖食譜、家鄉秘笈紀錄、公告卡隨機曝光結果、未處理事故、停售菜色、理賠及店長事件 |
| 每夜帳務 | `ledger`、`journal`、現金、庫存與貸款狀態 |
| 會計 | `accounting` 中的科目餘額、日記帳、週底稿、期末報表及資產清冊 |
| 成就 | `achievements` 中已解鎖項目、解鎖夜次／期數、待查看提示及帳務閱讀狀態 |

`normalizeState()` 是存檔邊界：合併預設值、清理未知菜色／事件、限制集合大小、修補舊版店面資料，並將舊版 30 夜結束狀態轉為可持續經營狀態。新增或更名欄位時不得只修改 `freshState()`；需同時更新正規化和遷移測試。

### 4.4 成就紀錄

`achievements.js` 以既有營運狀態推導 26 項港邊里程碑，已解鎖紀錄只保存 id、解鎖夜次與期數；提示佇列及日記／財報閱讀狀態用於非阻塞回饋和少量成就條件，不另存累計遊玩歷程。舊存檔載入時，能由現有資料確認的里程碑會靜默補登，避免一次跳出大量提示。成就不發放現金、折扣或其他經濟效果；不可逆重啟會清空當前世界的成就。

### 4.2 分店資料

分店以 `outlets[]` 管理。每個店面具有識別碼、業態、攤型、營業狀態、店長指派、專屬庫存與進價、安全設備、設備等級、聲望、暫停自動營運狀態及最近營運結果。業態商品由 `data.js` 的 `outletProducts` 提供，取得店面後依其業態初始化；不得以主店庫存覆蓋分店庫存。

### 4.3 場景派生資料

場景的主攤視覺尺寸由 `outlets[].tier` 與 `expansions` 計算。攤位世界座標、桌椅排列和視覺效果目前由靜態設定與渲染規則派生；不另寫入存檔。若未來引入可放置建築或可解鎖區塊，需新增明確 schema 與遷移，而不是在 renderer 內保存隱性狀態。

## 5. 遊戲階段與動作契約

現行主流程階段為：

```text
prep（備料與準備） → service（營業服務） → report（打烊與手記）
                                              │
                             選擇故事／週決策 ─┘ → 下一夜
```

主要操作由 `createGameEngine(state, { random })` 提供，包括開門、公告卡及宣傳結果、借還週轉金、服務菜色、客訴／事故處理、打烊收銀差異／秘密客／秘密稽查、主店與分店進貨、設備與攤型升級、員工／店長管理、故事選擇、週決策、結束當夜與重啟活動。

操作結果慣例：

```js
{ ok: boolean, changed: boolean, message: string }
```

條件不足、資金不足等預期結果用 `ok: false` 回傳，不應以例外控制正常遊戲流程。意外錯誤由瀏覽器動作邊界還原 state 快照並回饋玩家。亂數經由引擎選項注入，測試可使用固定序列驗證機率流程。

## 6. 經濟與會計設計

### 6.1 經濟回饋

- **收入：** 餐點售價、服務／小費、活動補助、模擬保險理賠收入與可辨認為店家現金盤盈的短溢收益。
- **變動成本：** 食材耗用、補貨與依事件調整的進貨成本。
- **固定／週期成本：** 租金、人事、水電瓦斯、保險、借款利息及分店維持費。
- **投資：** 設備、攤位改造、擴店與併購；投資可解鎖容量、商品與店面能力，也增加資金佔用或持續成本。
- **需求與風險：** 口碑、熟客、活動、天候、供應、稽查、奧客與同業聯盟共同影響當夜客流、成本或決策。

平衡原則為「額外收益伴隨成本、容量或風險」；公告卡與事件採有上限或有代價的選擇，避免不受限制的正收益循環。實際參數以 `data.js`、`campaign.js` 和引擎規則為準。

### 6.2 會計記錄

`accounting.js` 維護科目型態、正常餘額、分錄與報表。`postJournal()` 需驗證每筆交易借貸總額相等；常見映射包括現金、食材存貨、營收、銷貨成本、薪資租金能源、保險費、理賠應收、設備資產、折舊、借款與利息。已確認的顧客溢付款會原路退款，借記 4090「退款及銷貨折讓」並貸記現金；不明來源的盤盈借記現金、貸記 4040「現金短溢收益」。假鈔或漏收等短少借記 5510「現金短溢損失」、貸記現金。付費廣告、節目置入與名人接待費列 5410「行銷及宣傳費」；採訪免費，稽查獎勵列 4020，整改罰款列 5400。

會計狀態與遊戲現金／庫存／貸款同時存在，屬有意的操作模型與帳務投影；任何新增收支必須經過一個一致的更新路徑，並測試兩者勾稽。

遊戲使用內部科目編號及簡化的保險、稅務、折舊和報表假設；報表不等同正式 IFRS 財報或法定申報。新增報表前先定義科目映射、期末結轉、現金流分類與可勾稽測試。

### 6.3 收銀與宣傳的隨機事件

公告卡在 30 夜週期的固定日期出現。免費採訪、名人接待、短影音廣告與節目置入可提高曝光，但結果機率不同；效果會寫入當日 `marketCardOutcome`，在來客／口碑及日記中呈現。所有付費方案依選擇先列行銷成本（5410），效果不佳也不回沖支出。

打烊時最多觸發一種收銀短溢情境：假鈔／假幣、加價購短收、未辨認來源的盤盈，或已確認的顧客多收款退款。未辨認來源的盤盈才列 4040 收益；顧客多收款採「原銷售＋4090 折讓退款」留存可追溯分錄，不把應返還金額當成利潤。秘密客及秘密衛生稽查另按獨立機率結算；秘密客只調整口碑，稽查通過／未通過分別記入 4020 獎勵收入或 5400 整改費。所有隨機值由引擎注入的 `random` 來源取得，以可重現序列測試現金與科目餘額。

## 7. 攤型、安全與保險

`safety.js` 是攤型與保障判定的單一規則來源。攤型只能逐級升級；`getTierReadiness()` 驗證必要安全設備、人力與規模條件。容量和能源費用會隨攤型變化。

保險規則由攤型、店面業態、員工數與該期已繳保障快照共同決定。每期首夜計費；事故流程檢查保障快照，將符合條件的模擬理賠先列為應收，再於指定夜數後收款。離職人員的孤兒保單在期間末作調整並形成下一期收款。保費、理賠與事故成本都需進入帳務科目。

## 8. UI、Canvas 與可及性

- 管理面板以 DOM 節點建立；外部或遊戲資料以 `textContent` 顯示，避免把遊戲文字當成 HTML。
- 報表使用 `ui/reports.js`，維持日記、週底稿與週期財報的獨立渲染責任。
- 成就清單由 `ui/achievements.js` 建立，透過獨立原生 `dialog` 分類瀏覽；解鎖提示為輕量 toast，已解鎖全彩、未解鎖灰階，不阻塞營運流程。
- 場景由 Canvas 2D 畫出地面、攤位、角色與特效；命中測試將點擊映射為主店、分店或事件操作。
- 當夜營收牌固定在場景視窗，不跟隨相機旋轉；Canvas 交易浮標則錨定實際成交的主攤或自動營運分店，讓場景回饋與左側操作連在一起。
- 營收牌將商品銷售、小費與活動／手記收入分列；補助、理賠應收、收銀盤盈另外列示，短少與退款列為調整，不計入營業收入。牌面是收入摘要而非淨利；租金、人事、能源、食材及結帳事件造成的損益仍依每日帳本與結帳結果計算。
- 顧客結帳、分店自動銷售、補助／理賠應收及收銀調整均可產生短暫的分類浮標。浮標及平滑計數是執行期視覺資料，不新增存檔欄位；減少動態效果或暫停場景時，數字直接顯示最終值，不依賴動畫傳達資訊。
- Canvas 提供可讀標籤、鍵盤操作說明；對話框應支援鍵盤焦點返回與適當的 aria 狀態。
- 互動動畫需尊重 `prefers-reduced-motion`；玩家也可以暫停場景動畫。動畫不得是讀取重要狀態的唯一方式。
- 窄版 UI 應保持可觸控、避免工具列與事件提示互相遮蔽；重大操作回饋需能在觸控與鍵盤環境理解。

## 9. 錯誤、存檔與資料保存

- 目前存檔 schema 版本為 `5`，主存檔與舊存檔 key 定義在 `DATA`；舊版資料會遷移至預設結構，公告卡結果只有在日期、卡片 id 與當日選項相符時才會保留。
- 載入會捕捉 JSON 解析／Storage 讀取錯誤；無法恢復的損壞資料以備份路徑處理並回到新遊戲。
- 未知的未來 schema 不應被舊版安靜覆寫；寫入失敗要在 UI 顯示保存狀態。
- 明確重啟會嘗試移除目前、舊版及 `.corrupt-backup` 三個已知 key；任何一個移除失敗都需回報，且較新版 schema 必須完全跳過刪除與覆寫。
- 狀態集合有長度上限，防止長期遊玩讓 localStorage 無界增長。
- 不可在遊戲 log 或 docs 寫入玩家的實際存檔內容、認證資料或隱私資料。

## 10. 驗證策略

最低要求：

1. 執行 `npm test`；測試需使用 fresh state 或明確重置同一 state。
2. 存檔修改需覆蓋新存檔、舊版遷移、格式損壞、未知版本及容量錯誤。
3. 經濟／會計修改需覆蓋資金變化、分錄平衡、資產負債勾稽及週期結算。
4. 場景修改需覆蓋視覺 profile／命中測試資料，並檢查窄版和 reduced-motion 表現。
5. 對預期拒絕路徑與隨機事件使用可注入亂數建立可重現測試。

目前主要自動測試檔是 `tests/game.test.js`；包含可重現的宣傳成效、現金短溢、顧客退款、秘密客與衛生稽查路徑。具有瀏覽器特有行為的端到端測試仍屬後續品質工作。

## 11. 變更指南

新增一項核心功能時，依序確認：

1. 規則屬於 `data.js`、`campaign.js`、`safety.js`、`accounting.js` 或引擎中的哪一個責任域。
2. 是否改變 state shape、存檔 schema、週期或會計科目；若有，先規劃遷移及結帳行為。
3. UI 是否只負責呈現與派發動作，Canvas 是否只負責呈現與命中測試。
4. 成本、收益、資產、保險理賠是否完整記帳並與現金／庫存同步。
5. 新路徑是否有成功、失敗、極端值、載入／保存及可及性驗證。
6. 更新相應的架構、決策與里程碑文件，標明已完成或待辦狀態。
