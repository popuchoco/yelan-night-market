# 軟體設計說明（SDD）

**文件狀態：** 現行設計基線，依 2026-10-31 程式碼整理。
**系統名稱：** 夜嵐夜市  
**執行型態：** 瀏覽器端、單人、持續性經營模擬。

## 1. 目的與範圍

玩家經營港邊夜市主店並逐步發展店面、員工、設備、分店及財務能力。系統讓日常營運、每週策略、職安／食安事件與週期性帳務彼此連動。

遊戲以單一瀏覽器存檔為目前範圍，不提供帳號系統、跨裝置同步、多人共同經營或正式會計／保險用途。

## 2. 使用者與主要操作

- **玩家／店主：** 管理菜單、備料、設備、排班、攤型、安全、保險、店面與每週資本配置；處理客訴、職災、顧客意外及食安重大事件。
- **受管理分店：** 可由玩家自營，或在符合條件後交由店長自動處理例行工作。店長事件和其他重大決策仍須玩家選擇。
- **場景操作：** 透過 Canvas 點選主店或分店進入管理；旋轉、傾斜、縮放及有限平移檢視資料驅動的有限場景。接手船埠麵線後會解鎖可營運的東堤小巷，顧客／店員路線與攤位資料隨區塊啟用。

## 3. 核心使用情境

### 3.1 每夜營運

1. 營運面板從既有週焦點與目前階段推導「今晚一件事」；第 1–7 夜採較簡化的提示層級，玩家可忽略提示並照常進入其他面板。
2. 在準備階段選擇今晚菜色，檢視庫存與設備、人員狀況，完成每日公告卡選擇（僅排程夜晚出現）。
3. 開門時記錄固定營運費用，生成當夜顧客與事件。
4. 逐位服務顧客；依訂單消耗食材，更新營收、成本、小費、口碑與熟客。連續合胃口服務可顯示短暫連擊回饋；售完料理提供不含金額的場景提示。
5. 若發生客訴、職災或食安事件，依事件流程處理；保險保障只對符合條件的事件提供模擬理賠選項。
6. 打烊結算現金與帳務分錄，產生日記與故事選擇；結帳歸檔前將實際現金簿與當夜焦點摘要附在日記項目。進入新夜準備時，清楚標示前一夜現金流，不預告當夜未發生的收入；食安恢復期則標示剩餘客流影響夜數。
7. 每 30 夜結帳後，下一期第一夜會依前一期結局與最近一次週決策生成敘事回聲，並提供上一期財報入口。

### 3.2 每週決策

每經過七夜進入策略節點，可依目前資金與店況選擇擴店、招募、併購、保留現金等方案。決策卡列出一次性費用、選擇後每夜固定承諾、未來七夜新增固定支出、至少需要新增的每夜貢獻，以及扣除投資後的固定支出續航。承諾估值排除天候、稽查、宣傳與清潔等單夜偶發項目，並把每期保費按 30 夜攤提；這仍不是盈虧預測，因為食材、事故與分店開門／店長等後續安排需分開考量。併購預覽會明確提示分店開門後另加能源費及之後可能的人事、升級和保費。完成四次併購後，第五次可用 NT$ 1,480 接手船埠麵線；該選擇增加每夜 NT$ 38 的分店租金，並解鎖東堤小巷與專屬麵線商品。每週風險摘要預設收合，僅於週決策頁顯示；展開後檢視事故、保障、理賠及下期保費。現金續航醒目標示為估算、非保證，且未含備料、事件／事故與分店營運變動。週轉金依週期規則限制借用及還款，未還本金持續產生模擬利息。每次選擇後會建立一項與方向相符的週焦點；它追蹤服務來客、合胃口服務、分店商品銷售夜或正現金夜，不另加強制按鈕。跨過一半及達標時各提示一次；週焦點成果與借貸平衡一起歸檔於日記簿及每週工作底稿；完成可得口碑 +2、熟客 +1，未完成不扣資源或口碑。

### 3.3 每 30 夜結帳

每 30 夜形成一期，產生主要損益、權益變動、財務狀況及現金流量報表；折舊與攤銷按日提列。保險費在每期首夜依攤型與人員狀態計入；符合條件的離職保單於期末工作底稿調整可收回金額，次期收款沖銷應收。結帳後世界繼續進入下一期。

### 3.4 從頭開始

玩家在遊戲說明最後的「09｜重啟」按下重新開始後，系統只顯示確認視窗，不立即變更狀態。取消或關閉視窗不影響遊戲。確認後關閉兩個對話框，清除目前存檔、舊版存檔與損壞備份，呼叫引擎重置同一個 state root，清空場景顧客、回到營運面板並將第 1 夜新進度寫入存檔。

若載入結果為 `unsupported-version`，重啟不得呼叫刪除或寫入存檔操作；只重置本次執行中的記憶體 state，並提示較新版存檔完整保留。此路徑不代表可以遷移或讀取該新版存檔。

## 4. 遊戲狀態設計

### 4.1 狀態根

`state.js` 的 `freshState()` 建立遊戲根物件。核心欄位群組如下：

| 欄位 | 內容 |
| --- | --- |
| 進度 | `schemaVersion`、`day`、`phase`、`endingId`、故事／週決策紀錄 |
| 週期節奏 | `weeklyFocus` 及各夜 `journal[].weeklyFocus`：目標類型、開始夜、累積值與結算結果；引擎提示佇列只存在執行期 |
| 日記摘要 | `journal[]` 可選 `cashbook`：完成當夜後保存現金簿、營運與焦點快照；舊手記可由會計日記帳回補可用的現金流 |
| 玩家經營指標 | `coins`、`fame`、`regulars`、`cozy`、收入與營業結果 |
| 主店營運 | `stock`、`stockCost`、`equipment`、`staff`、`upgrades`、`expansions` |
| 店面組合 | `acquisitions`（0–5）、`acquisitionTypes`、`outlets[]`；主店與分店保有各自商品、人員、設備、保險和營業狀態。區塊解鎖由 outlet type 推導，不另存區塊座標 |
| 事件與菜色 | 已解鎖食譜、家鄉秘笈紀錄、公告卡隨機曝光結果、未處理事故、停售菜色、理賠及店長事件 |
| 每夜帳務 | `ledger`、`journal`、現金、庫存與貸款狀態 |
| 會計 | `accounting` 中的科目餘額、日記帳、週底稿、期末報表及資產清冊 |
| 成就 | `achievements` 中已解鎖項目、解鎖夜次／期數、待查看提示及帳務閱讀狀態 |

`normalizeState()` 是存檔邊界：合併預設值、清理未知菜色／事件、限制集合大小、修補舊版店面資料，並將舊版 30 夜結束狀態轉為可持續經營狀態。新增或更名欄位時不得只修改 `freshState()`；需同時更新正規化和遷移測試。

`progression.js` 的 `getOnboardingTier(day)` 與 `getTonightHint(state)` 是由 `day`、`phase` 及 `weeklyFocus` 推導的唯讀資料，不保存到 state，也不增加 schema。週焦點結算結果可選帶入 `status`、`remaining`、`unit` 與白話 `summary`；舊結果由正規化函式重新推導，缺少這些欄位不影響舊存檔載入。

### 4.4 成就紀錄

`achievements.js` 以既有營運狀態推導 26 項港邊里程碑，已解鎖紀錄只儲存 id、解鎖夜次與期數；提示佇列及日記／財報閱讀狀態用於非阻塞回饋和少量成就條件，不另存累計遊玩歷程。舊存檔載入時，能由現有資料確認的里程碑會靜默補登，避免一次跳出大量提示。成就不發放現金、折扣或其他經濟效果；不可逆重啟會清空目前世界的成就。

### 4.2 分店資料

分店以 `outlets[]` 管理。每個店面具有識別碼、業態、攤型、營業狀態、店長指派、專屬庫存與進價、安全設備、設備等級、聲望、暫停自動營運狀態及最近營運結果。業態商品由 `data.js` 的 `outletProducts` 提供，取得店面後依其業態初始化；不得以主店庫存覆蓋分店庫存。

### 4.3 場景派生資料

場景的主攤視覺尺寸由 `outlets[].tier` 與 `expansions` 計算；第 1–7 夜的相機 profile 將縮遠下限固定為 1、平移上限設為 0，並隱藏縮遠與平移按鈕、同步調整桌機／手機操作提示，仍允許旋轉與放大；第 8 夜起相機最小 zoom 與 pan 上限由 `expansions + 已接手分店數` 對照 `DATA.camera.progressLevels` 派生，遠景及領地線也由既有進度與靜態設定繪製。`DATA.marketBlocks` 定義港邊主巷與東堤小巷；取得 `type: "noodle"` 分店即解鎖東堤區塊，`getMarketStalls()` 再供攤位繪製與 outlet 映射使用。路線由 `getOutletCrowdRoutes()` 與 `getMarketStaffWaypoints()` 派生；只有已解鎖區塊提供的隊伍／店員路線會加入場景。相機狀態、遠景燈點、區塊幾何及解鎖旗標不另寫入存檔；區塊幾何是靜態資料，解鎖由既有 outlet 派生。

## 5. 遊戲階段與動作契約

現行主流程階段為：

```text
prep（備料與準備） → service（營業服務） → report（打烊與手記）
                                              │
                               選擇故事 → 下一夜
                                  │
                          每七夜・週工作底稿
                                  ↓
                    週決策 → 新週焦點 → prep
```

每 30 夜另完成期末調整與主要財務報表；它是較長週期的回顧點，不會停止世界循環。

主要操作由 `createGameEngine(state, { random })` 提供，包括開門、公告卡及宣傳結果、借還週轉金、服務菜色、客訴／事故處理、打烊收銀差異／秘密客／秘密稽查、主店與分店進貨、設備與攤型升級、員工／店長管理、故事選擇、週決策、結束當夜與重啟活動。

操作結果慣例：

```js
{ ok: boolean, changed: boolean, message: string }
```

條件不足、資金不足等預期結果用 `ok: false` 回傳，不應以例外控制正常遊戲流程。意外錯誤由瀏覽器動作邊界還原 state 快照並回饋玩家。亂數經由引擎選項注入，測試可使用固定序列驗證機率流程。

## 6. 經濟與會計設計

### 6.1 經濟回饋

- **收入：** 餐點售價、服務／小費、活動補助、模擬保險理賠收入與可辨認為店家現金盤盈的短溢收益。
- **變動成本：** 食材耗用、補貨與依事件調整的進貨成本。
- **固定／週期成本：** 租金、人事、水電瓦斯、保險、借款利息及分店維持費。
- **投資：** 設備、店面裝修、擴店與併購；投資可解鎖容量、商品與店面能力，也增加資金佔用或持續成本。
- **需求與風險：** 口碑、熟客、活動、天候、供應、稽查、奧客與同業聯盟共同影響當夜客流、成本或決策。

平衡原則為「額外收益伴隨成本、容量或風險」；公告卡與事件採有上限或有代價的選擇，避免不受限制的正收益循環。實際參數以 `data.js`、`campaign.js` 和引擎規則為準。

### 6.2 會計記錄

`accounting.js` 維護科目型態、正常餘額、分錄與報表。`postJournal()` 需驗證每筆交易借貸總額相等；常見映射包括現金、食材存貨、營收、銷貨成本、薪資租金能源、保險費、理賠應收、設備資產、折舊、借款與利息。已確認的顧客溢付款會原路退款，借記 4090「退款及銷貨折讓」並貸記現金；不明來源的盤盈借記現金、貸記 4040「現金短溢收益」。假鈔或漏收等短少借記 5510「現金短溢損失」、貸記現金。付費廣告、節目置入與名人接待費列 5410「行銷及宣傳費」；採訪免費，稽查獎勵列 4020，限期改善罰款列 5400。

會計狀態與遊戲現金／庫存／貸款同時存在，屬有意的操作模型與帳務投影；任何新增收支必須經過一個一致的更新路徑，並測試兩者勾稽。

遊戲使用內部科目編號及簡化的保險、稅務、折舊和報表假設；報表不等同正式 IFRS 財報或法定申報。新增報表前先定義科目映射、期末結轉、現金流分類與可勾稽測試。

### 6.3 收銀與宣傳的隨機事件

公告卡在 30 夜週期的固定日期出現。免費採訪、名人接待、短影音廣告與節目置入可提高曝光，但結果機率不同；效果會寫入當日 `marketCardOutcome`，在來客／口碑及日記中呈現。所有付費方案依選擇先列行銷成本（5410），效果不佳也不回沖支出。

打烊時最多觸發一種收銀短溢情境：假鈔／假幣、加價購短收、未辨認來源的盤盈，或已確認的顧客多收款退款。未辨認來源的盤盈才列 4040 收益；顧客多收款採「原銷售＋4090 折讓退款」留存可追溯分錄，不把應返還金額當成利潤。秘密客及秘密衛生稽查另按獨立機率結算；秘密客只調整口碑，稽查通過／未通過分別記入 4020 獎勵收入或 5400 限期改善費。所有隨機值由引擎注入的 `random` 來源取得，以可重現序列測試現金與科目餘額。

## 7. 攤型、安全與保險

`safety.js` 是攤型與保障判定的單一規則來源。攤型只能逐級升級；`getTierReadiness()` 驗證必要安全設備、人力與規模條件。容量和能源費用會隨攤型變化。

保險規則由攤型、店面業態、員工數與該期已繳保障快照共同決定。每期首夜計費；事故流程檢查保障快照，將符合條件的模擬理賠先列為應收，再於指定夜數後收款。離職人員的孤兒保單在期間末作調整並形成下一期收款。保費、理賠與事故成本都需進入帳務科目。理賠收款時依原事故類型將改善後續摘要寫入該夜日記，回應安全作業調整、動線改善或食安恢復；這段敘事不增加口碑、熟客、賠款或其他經濟結果。

## 8. UI、Canvas 與可及性

- 管理面板以 DOM 節點建立；外部或遊戲資料以 `textContent` 顯示，避免把遊戲文字當成 HTML。
- 報表使用 `ui/reports.js`，維持日記、週底稿與週期財報的獨立渲染責任。
- `ui/engagement.js` 以單張「今晚一件事」卡呈現階段行動及本週焦點剩餘量；第 1–7 夜不強制導覽，準備／營業完整收支明細改用原生 `details` 收合，摘要仍顯示預估淨額或當夜收入／食材耗用，進階面板持續可由分頁進入。週焦點結算明確呈現達標、接近或未完成與簡短摘要；重要狀態以文字、數值及視覺共同表達，不只依賴顏色。
- 準備階段的「昨夜現金簿」以收入、支出及淨流入展示前一夜實際現金資料；商品、小費、活動與手記收入作次要拆分。金額來自日記簿結帳快照或對應日記帳分錄，不從當夜預估帳本假設實收。
- 第一夜尚無前夜實際現金收付時隱藏場景現金簿，不以破折號佔位；第 2 夜起只有前一日存在現金日記帳且目前為準備階段時顯示，可由玩家關閉至下一夜。
- 週決策續航只用於固定成本風險提示；當期保費按 30 夜攤提，單夜天候／稽查／宣傳／清潔不當作持續承諾。醒目單行說明「估算非保證：只計固定支出，未含備料、事件／事故與分店營運變動」，不將現金續航偽裝成保證或精確淨利預測。風險卡使用原生 `details`／`summary` 預設收合，僅在週決策頁出現，降低與昨夜現金簿同屏時的資訊密度。
- 週風險摘要回顧近七夜事故、當期保障快照、理賠應收與依當前營運狀態估算的下期保費；理賠後續只在已收款當夜寫入日記，不新增持續狀態或經濟效果。
- 週焦點里程碑提示每一焦點只按跨越 50% 與 100% 門檻暫存於引擎執行期並呈現一次；重新載入後不回放舊 toast，週結算仍是保存進度的正式紀錄。
- 可公開的成就若有明確單一計數器，卡片顯示目前值及可存取進度列；隱藏成就不提供任何進度資訊。
- 成就清單由 `ui/achievements.js` 建立，透過獨立原生 `dialog` 分類瀏覽；解鎖提示為輕量 toast，已解鎖全彩、未解鎖灰階，不阻塞營運流程。
- 場景由 Canvas 2D 畫出地面、攤位、角色、遠景剪影與特效；相機活動範圍依擴店／已接手分店進度逐級放寬，受設定的最小 zoom 和 viewport 比例 pan 界限約束。主店擴店後會畫出地面領地提示；東堤小巷解鎖後會加入新場景塊、店面、道具、環境／隊伍／店員路線，並沿用既有攤位管理與收入帳務。此為有界的資料驅動地圖，不是無限地圖生成。
- Canvas 命中測試、事件提示 anchor、角色和物件繪製共用同一個 `project()` 相機轉換；平移後要一起檢查攤位／事件點擊，不可只改 Canvas 圖像而漏調 DOM 提示定位。
- 桌機用一般拖曳旋轉、Shift／右鍵拖曳或 WASD 平移、滾輪縮放；手機以 44px 方向按鈕平移，並可透過相機工具旋轉、俯仰、縮放及重設。平移／旋轉均有替代按鈕或鍵盤操作，不以單一精細手勢作為唯一入口。
- 首週相機收窄探索範圍是衍生規則，不保存教學旗標；縮遠與平移範圍為零，避免新手尚未理解主要營運流程就看見遠區。第 8 夜才依擴店及分店逐步放寬。
- `audio.js` 使用 Web Audio API 延遲產生可選、低音量環境音與操作提示音；預設關閉，明確開啟後才於互動時建立音訊環境。切換分頁時暫停音訊，關閉時停止音景節點；瀏覽器不支援時不阻斷遊戲。
- 連續合胃口出餐使用操作提示音的遞增音高，屬純回饋，不增加服務收入、熟客或口碑；客訴或新夜會中斷連擊。
- `scene/revenue.js` 除金額交易浮標外，也支援非財務服務提示。缺貨訊息以灰綠中性色顯示，不呈現零元或寫入營收；連擊使用既有當夜記憶體計數，仍沿用原有音效開關。場景暫停或減少動態效果時，不繪製浮動動畫，但保留 live-region 文字播報。
- 當夜營收牌固定在場景視窗，不跟隨相機旋轉；Canvas 交易浮標則錨定實際成交的主攤或自動營運分店，讓場景回饋與左側操作連在一起。
- 營收牌將商品銷售、小費與活動／手記收入分列；補助、理賠應收、收銀盤盈另外列示，短少與退款列為調整，不計入營業收入。牌面是收入摘要而非淨利；租金、人事、能源、食材及結帳事件造成的損益仍依每日帳本與結帳結果計算。
- 顧客結帳、分店自動銷售、補助／理賠應收及收銀調整均可產生短暫的分類浮標。浮標及平滑計數是執行期視覺資料，不新增存檔欄位；減少動態效果或暫停場景時，數字直接顯示最終值，不依賴動畫傳達資訊。
- Canvas 提供可讀標籤、鍵盤操作說明；相機按鈕須有方向性 aria-label，手機平移目標至少 44px，鍵盤可聚焦 Canvas 後以 WASD 平移、方向鍵旋轉／俯仰。對話框應支援鍵盤焦點返回與適當的 aria 狀態。
- 互動動畫需尊重 `prefers-reduced-motion`；玩家也可以暫停場景動畫。動畫不得是讀取重要狀態的唯一方式。
- 場景暫停或系統減少動態效果時，以最多每秒 10 次的頻率重繪靜態畫面，保留相機和互動回饋；效能提升需另以實機量測，不從節流本身推定數據。
- 窄版 UI 應保持可觸控、避免工具列與事件提示互相遮蔽；重大操作回饋需能在觸控與鍵盤環境理解。

## 9. 錯誤、存檔與資料儲存

- 目前存檔 schema 版本為 `7`，主存檔與舊存檔 key 定義在 `DATA`；舊版資料會遷移至預設結構，週焦點依目前週次與週決策補入；公告卡結果只有在日期、卡片 id 與當日選項相符時才會保留。第 7 版支援新的麵線業態與第五次併購上限；區塊解鎖狀態由 outlet 推導，地圖靜態資料不重複寫入存檔。既有 `cashbook` 仍是可選欄位，舊日記可直接讀取。
- 載入會捕捉 JSON 解析／Storage 讀取錯誤；無法恢復的損壞資料以備份路徑處理並回到新遊戲。
- 未知的未來 schema 不應被舊版安靜覆寫；寫入失敗要在 UI 顯示儲存狀態。
- 明確重啟會嘗試移除目前、舊版及 `.corrupt-backup` 三個已知 key；任何一個移除失敗都需回報，且較新版 schema 必須完全跳過刪除與覆寫。
- 狀態集合有長度上限，防止長期遊玩讓 localStorage 無界增長。
- 不可在遊戲 log 或 docs 寫入玩家的實際存檔內容、認證資料或隱私資料。

## 10. 驗證策略

最低要求：

1. 執行 `npm test`；測試需使用 fresh state 或明確重置同一 state。
2. 存檔修改需覆蓋新存檔、舊版遷移、格式損壞、未知版本及容量錯誤。
3. 經濟／會計修改需覆蓋資金變化、分錄平衡、資產負債勾稽及週期結算。
4. 場景修改需覆蓋視覺／相機 profile、pan 邊界與命中測試資料；手動驗收窄版、多相機角度及 reduced-motion 表現。
5. 對預期拒絕路徑與隨機事件使用可注入亂數建立可重現測試。

目前測試由 `npm test` 執行多個模組檔，涵蓋遊戲、會計、成就、週焦點、engagement DOM、場景與跨期 smoke；總計 94 項通過。仍缺少重啟確認、鍵盤焦點與實際瀏覽器儲存互動的端到端測試；手機／真人體驗也不能由單元測試取代。

## 11. 變更指南

新增一項核心功能時，依序確認：

1. 規則屬於 `data.js`、`campaign.js`、`safety.js`、`accounting.js` 或引擎中的哪一個責任域。
2. 是否改變 state shape、存檔 schema、週期或會計科目；若有，先規劃遷移及結帳行為。
3. UI 是否只負責呈現與派發動作，Canvas 是否只負責呈現與命中測試。
4. 成本、收益、資產、保險理賠是否完整記帳並與現金／庫存同步。
5. 新路徑是否有成功、失敗、極端值、載入／儲存及可及性驗證。
6. 更新相應的架構、決策與里程碑文件，標明已完成或待辦狀態。
